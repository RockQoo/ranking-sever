랭킹 서버 측정 결과

Redis Sorted Set vs MySQL(InnoDB), MySQL 순위 테이블 배치 재계산, Kafka → Redis 멱등 반영 · 2026-10-16 ~ 10-18

환경요약순차 지연동시 처리량 영속화깊은 페이지순위 테이블Kafka한계

측정 환경

  • 같은 PC. 클라이언트는 Windows 11의 .NET 10, 서버는 WSL2 Ubuntu 26.04
  • Redis 8.0.5 (기본 설정: AOF 꺼짐) · MySQL 8.4.11 (기본 설정: innodb_flush_log_at_trx_commit=1, buffer pool 128MB) · Kafka 4.3.1 (KRaft 단일 노드)
  • 데이터: 유저 10만 / 100만 명, 점수 0~999,999 균등 난수 (seed 42). 정렬은 점수 내림차순, 동점이면 user_id 내림차순
  • localhost 왕복이 약 0.2ms라 Redis 수치는 대부분 왕복 시간이다
  • 각 조건 1회 측정 → 몇 배 차이인지로만 읽는다

왜: Redis ZSET의 skiplist는 링크마다 건너뛰는 원소 수(span)를 저장해 순위·offset 위치를 O(log N)에 찾는다. InnoDB B+Tree는 하위 원소 수가 없어서 앞에 있는 행을 세거나 읽고 버려야 한다 → O(순위), O(offset).

설계: 실시간 순위는 Redis, 원본과 시즌 정산은 DB. 이벤트가 많으면 Kafka로 분리하고 반영을 멱등으로. MySQL만 써야 하면 순위 테이블을 배치로 만들어 바꿔치기한다.

  • 내 순위: Redis는 인원이 10배 늘어도 그대로(O(log N)). MySQL COUNT는 내 앞 사람 수만큼 인덱스를 읽는다 → 상위 1%는 1ms, 하위 1%는 64ms. EXPLAIN은 ix_score 범위 스캔(커버링), rows ≈ 내 순위

5. 순위 테이블 배치 재계산 + 바꿔치기 — MySQL, 100만 명 (2026-10-18)

  • 점수는 원본 ranking에 쌓고, 주기적으로 순위를 계산해 ranking_snapshot(user_id PK, score, rnk UNIQUE)에 넣는다. 게임은 순위 테이블만 조회
  • 재계산: 새 테이블에 INSERT … SELECT user_id, score, ROW_NUMBER() OVER (ORDER BY score DESC, user_id DESC) FROM ranking → ANALYZE TABLE → RENAME TABLE ranking_snapshot TO …_old, ranking_snapshot_new TO ranking_snapshot (한 문장이라 원자적)
  • 조회: 내 순위는 PK, 상위 N명·깊은 페이지·주변은 rnk BETWEEN 범위

  • 효과는 "순위를 미리 계산"에서 나온다. 내 순위 35~66ms → 0.65ms, 동시 처리 250 → 13,521건/초. 깊은 페이지도 OFFSET 대신 rnk 범위라 순위와 무관. 대가는 재계산 주기만큼 순위가 늦다는 것
  • 바꿔치기는 속도가 아니라 조회 안전성 때문이다. TRUNCATE 후 채우면 그 사이 조회의 88%가 "랭킹에 없음". 바꿔치기는 항상 이전 아니면 새 테이블을 봐서 0건
  • InnoDB는 한 트랜잭션 DELETE + INSERT도 실패가 없다(MVCC로 커밋 전까지 이전 행을 읽음). 대신 3배 느리고 undo가 쌓인다. MSSQL 기본 설정(READ COMMITTED, 스냅숏 격리 꺼짐)이면 이 방식은 조회가 커밋까지 막힌다 → MSSQL에서 리네임 방식을 쓰는 이유 (MSSQL은 측정 안 함)

함정 세 가지

  • 재계산 세션은 READ COMMITTED. 기본(REPEATABLE READ + binlog)에서는 INSERT … SELECT가 원본 행마다 공유 잠금을 걸어 재계산 내내 점수 갱신이 막히고(최대 4.5초) 데드락도 난다
  • 바꿔치기 전에 ANALYZE TABLE. 새로 채운 테이블은 통계가 "빈 테이블"(rows=21)이라 rnk 인덱스를 두고 ALL + Using filesort를 골랐다. 상위 100명 첫 조회 95ms(정상 0.8ms). InnoDB 백그라운드 통계 재계산 전까지 느리다
  • RENAME은 메타데이터 잠금(MDL)이 필요하다. 순위 테이블을 읽은 트랜잭션이 열려 있으면 RENAME이 기다리고, 그 뒤 조회도 전부 줄을 선다. 긴 정산·통계 쿼리와 시각을 겹치지 않고 lock_wait_timeout을 짧게 걸어 재시도한다(기본값 1년)

6. Kafka → Redis 랭킹 반영 — 이벤트 20만 건, 유저 1만 명

  • 토픽 score-events 파티션 4개, 키 = user_id → 같은 유저는 같은 파티션 → 유저별 순서 보장
  • 프로듀서 acks=all, enable.idempotence=true
  • 컨슈머: 자동 커밋 끔, 500건 배치 → Redis 반영 → 반영 후 커밋 (at-least-once)
  • 멱등 반영: 이벤트에 유저별 seq, Lua 스크립트로 "마지막 seq보다 클 때만 ZINCRBY + seq 기록"을 원자적으로
단계결과
발행초당 약 14만~23만 건(실행마다 차이), 전송 실패 0. 파티션별 약 5만 건씩
컨슈머 A 장애 재현3만 건 반영, 2만 건까지만 커밋하고 종료

  • 프로듀서 멱등성은 브로커에 같은 메시지가 두 번 쌓이는 것만 막는다. 컨슈머가 다시 받는 중복은 애플리케이션이 막는다
  • B1·B2 동시 시작에서 B2가 먼저 합류해 파티션 4개를 다 처리했다. 파티션이 둘로 나뉘는 모습은 이번 실행에서 확인하지 못했다

측정의 한계

  • 클라이언트와 서버가 같은 PC라 네트워크 지연이 실제보다 작고, CPU를 나눠 쓴다
  • 모두 기본 설정. MySQL buffer pool(128MB)에 100만 명 테이블(score-only 약 75MB)이 다 들어가 디스크 읽기는 거의 없었을 것(확인 안 함)
  • 각 조건 1회 측정. 수치는 차이의 크기(몇 배)를 보는 용도
