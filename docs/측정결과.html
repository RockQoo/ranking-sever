랭킹 서버 측정 결과

Redis Sorted Set vs MySQL(InnoDB) · MySQL 순위 테이블 배치 재계산 · Kafka → Redis 멱등 반영 · 2026-10-19 (MySQL 쿼리는 저장 프로시저)

환경요약순차 지연동시 처리량 영속화깊은 페이지순위 테이블Kafka한계

측정 환경

  • 같은 PC. 클라이언트는 Windows 11의 .NET 10, 서버는 WSL2 Ubuntu 26.04
  • Redis 8.0.5 (기본 설정: AOF 꺼짐) · MySQL 8.4.11 (기본 설정: innodb_flush_log_at_trx_commit=1, buffer pool 128MB) · Kafka 4.3.1 (KRaft 단일 노드)
  • MySQL 테이블·인덱스는 sql/schema.sql, 쿼리는 sql/procedures.sql의 저장 프로시저. C#은 CALL만 한다
  • 데이터: 유저 100만 명, 점수 0~999,999 균등 난수 (seed 42). 정렬은 점수 내림차순, 동점이면 user_id 내림차순
  • localhost 왕복이 약 0.2ms라 Redis 수치는 대부분 왕복 시간이다
  • 각 조건 1회 측정 → 몇 배 차이인지로만 읽는다

왜: Redis ZSET의 skiplist는 링크마다 건너뛰는 원소 수(span)를 저장해 순위·offset 위치를 O(log N)에 찾는다. InnoDB B+Tree는 하위 원소 수가 없어서 앞에 있는 행을 세거나 읽고 버려야 한다 → O(순위), O(offset).

설계: 실시간 순위는 Redis, 원본과 시즌 정산은 DB. MySQL만 써야 하면 순위 테이블을 배치로 만들어 바꿔치기한다(대신 재계산 주기만큼 늦음). 이벤트가 많으면 Kafka로 분리하고 반영을 멱등으로.

4. 깊은 페이지 — 닉네임 포함 랭킹 목록, offset부터 10명

"랭킹 더 보기" 화면처럼 (user_id, 닉네임, 점수)를 보여 준다. 닉네임은 일반적인 구조대로 별도 테이블 users(user_id PK, nickname)에 있다.

  • Redis: ZREVRANGE + 닉네임 해시 HMGET (2회 왕복)
  • MySQL 단순 JOIN (sp_ranking_get_page_named): ranking JOIN users … ORDER BY score DESC, user_id DESC LIMIT 10 OFFSET n — 가장 흔하게 짜는 쿼리
  • MySQL 지연 조인 (sp_ranking_get_page_named_deferred): 안쪽에서 인덱스만으로 10명을 고르고 그 10명만 users와 JOIN
  • MySQL 순위 테이블 (sp_snapshot_get_page_named): rnk BETWEEN n+1 AND n+10 + users JOIN

단순 JOIN이 가장 느린 이유: MySQL은 LIMIT … OFFSET을 JOIN이 끝난 결과에 적용한다. 버릴 90만 행도 하나하나 users를 PK로 찾아 JOIN한 뒤 버린다 → 90만 번의 PK 조회.

지연 조인: 안쪽 쿼리가 커버링 인덱스만 읽어 10명을 고르고 그 10명만 JOIN → 9배 빠르다. 그래도 offset만큼 읽고 버리는 O(offset)은 남는다.

순위 테이블: rnk 범위로 그 위치를 바로 찾아 어느 offset이든 0.7ms.

다음 페이지만 필요하면 키셋 페이지네이션도 있다: 직전 페이지 마지막 행의 (score, user_id)로 WHERE score < @s OR (score = @s AND user_id < @u) ORDER BY score DESC, user_id DESC LIMIT 10. "N번째 페이지로 바로 이동"은 안 된다. (측정하지 않음)

5. 순위 테이블 배치 재계산 + 바꿔치기 — MySQL, 100만 명

  • 점수는 원본 ranking에 쌓고, 주기적으로 순위를 계산해 ranking_snapshot(user_id PK, score, rnk UNIQUE)에 넣는다. 게임은 순위 테이블만 조회
  • 재계산 sp_snapshot_rebuild_swap: CREATE TABLE …_new LIKE ranking_snapshot → INSERT … SELECT user_id, score, ROW_NUMBER() OVER (ORDER BY score DESC, user_id DESC) FROM ranking → ANALYZE TABLE → RENAME TABLE ranking_snapshot TO …_old, ranking_snapshot_new TO ranking_snapshot (한 문장이라 원자적)
  • 조회: 내 순위는 PK, 상위 N명·깊은 페이지는 rnk BETWEEN 범위, 주변은 자기 JOIN

  • 효과는 "순위를 미리 계산"에서 나온다. 내 순위 34~64ms → 0.7ms, 동시 처리 229 → 11,714건/초. 깊은 페이지도 OFFSET 대신 rnk 범위라 순위와 무관. 대가는 재계산 주기만큼 순위가 늦다는 것
  • 바꿔치기는 속도가 아니라 조회 안전성 때문이다. TRUNCATE 후 채우면 그 사이 조회의 90%가 "랭킹에 없음". 바꿔치기는 항상 이전 아니면 새 테이블을 봐서 0건
  • InnoDB는 한 트랜잭션 DELETE + INSERT도 실패가 없다(MVCC로 커밋 전까지 이전 행을 읽음). 대신 2.5배 느리고 undo가 쌓인다. MSSQL 기본 설정(READ COMMITTED, 스냅숏 격리 꺼짐)이면 이 방식은 조회가 커밋까지 막힌다 → MSSQL에서 리네임 방식을 쓰는 이유 (MSSQL은 측정 안 함)

함정 세 가지

  • 재계산 세션은 READ COMMITTED. 기본(REPEATABLE READ + binlog)에서는 INSERT … SELECT가 원본 행마다 공유 잠금을 걸어 재계산 내내 점수 갱신이 막히고(최대 5.1초) 데드락도 난다
  • 바꿔치기 전에 ANALYZE TABLE. 새로 채운 테이블은 통계가 "빈 테이블"(rows=20)이라 rnk 인덱스를 두고 ALL + Using filesort를 골랐다. 상위 100명 첫 조회 106ms(정상 0.8ms). InnoDB 백그라운드 통계 재계산 전까지 느리다
  • RENAME은 메타데이터 잠금(MDL)이 필요하다. 순위 테이블을 읽은 트랜잭션이 열려 있으면 RENAME이 기다리고, 그 뒤 조회도 전부 줄을 선다. 긴 정산·통계 쿼리와 시각을 겹치지 않고 lock_wait_timeout을 짧게 걸어 재시도한다(기본값 1년)

6. Kafka → Redis 랭킹 반영 — 이벤트 20만 건, 유저 1만 명 (2026-10-16)

  • 토픽 score-events 파티션 4개, 키 = user_id → 같은 유저는 같은 파티션 → 유저별 순서 보장
  • 프로듀서 acks=all, enable.idempotence=true
  • 컨슈머: 자동 커밋 끔, 500건 배치 → Redis 반영 → 반영 후 커밋 (at-least-once)
  • 멱등 반영: 이벤트에 유저별 seq, Lua 스크립트로 "마지막 seq보다 클 때만 ZINCRBY + seq 기록"을 원자적으로

측정의 한계

  • 클라이언트와 서버가 같은 PC라 네트워크 지연이 실제보다 작고, CPU를 나눠 쓴다
  • 모두 기본 설정. MySQL buffer pool(128MB)에 100만 명 테이블이 다 들어가 디스크 읽기는 거의 없었을 것(확인 안 함)
  • 각 조건 1회 측정. 수치는 차이의 크기(몇 배)를 보는 용도
