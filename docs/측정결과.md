# 측정 결과와 해석 (상세)

게임 랭킹을 **Redis Sorted Set**과 **MySQL(InnoDB)** 으로 구현해 비교한 상세 기록이다. 결론만 보려면 [README](../README.md)를, 셋팅은 [SETUP.md](../SETUP.md)를 본다. 측정 원본은 `results/` 폴더에 있다.

## 구성

| 경로 | 내용 |
|---|---|
| `sql/schema.sql` | MySQL 테이블·인덱스 (`ranking`, `ranking_snapshot`, `users`) |
| `sql/procedures.sql` | MySQL 저장 프로시저. 게임 서버는 `CALL`로만 호출한다 |
| `src/Ranking.Core` | `IRankingStore`와 구현 3개: `RedisRankingStore`, `MySqlRankingStore`(실시간), `MySqlSnapshotRankingStore`(배치 순위 테이블) |
| `src/Ranking.Bench` | 벤치마크. 저장소끼리 결과가 같은지 확인한 뒤 측정 |
| `src/Ranking.Api` | ASP.NET Core Minimal API 랭킹 서버. 저장소는 설정으로 고른다 |
| `src/Ranking.Kafka` | Kafka → Redis 랭킹 반영 데모. at-least-once 재전달과 멱등 반영 확인 |

정렬 기준은 모든 구현이 같다: **점수 내림차순, 동점이면 user_id 내림차순**.
Redis ZSET은 동점일 때 member 사전순으로 정렬하므로 member를 `D10` 고정 폭 문자열로 저장해 숫자 순서와 맞췄다.

## 기능별 구현

| 기능 | Redis | MySQL 실시간 (SP) |
|---|---|---|
| 점수 갱신 | `ZADD` — O(log N) | `sp_ranking_set_score`: `INSERT … ON DUPLICATE KEY UPDATE` + `(score, user_id)` 인덱스 갱신 — O(log N) + 커밋 fsync |
| 내 순위 | `ZREVRANK` — O(log N) | `sp_ranking_get_rank`: 나보다 앞선 행을 `COUNT(*)` (인덱스 범위 스캔) — **O(내 순위)** |
| 내 순위 (비교용) | — | `sp_ranking_get_rank_window`: `ROW_NUMBER() OVER (ORDER BY …)` — 매번 전체 정렬, O(N log N) |
| 상위 N명 | `ZREVRANGE 0 N-1 WITHSCORES` — O(log N + N) | `sp_ranking_get_top`: `ORDER BY score DESC, user_id DESC LIMIT N` — 인덱스 역방향 스캔 |
| 깊은 페이지 (offset부터 N명) | `ZREVRANGE offset offset+N-1` — O(log N + N) | `sp_ranking_get_page`: `LIMIT N OFFSET offset` — 앞의 offset개를 읽고 버림, **O(offset)** |
| 내 주변 ±k | `ZREVRANK` → `ZREVRANGE` (2회 왕복) | `sp_ranking_get_around`: 순위 `COUNT` → 위·아래 `LIMIT k` UNION (SP 하나, 1회 왕복) |

MySQL 순위 테이블 방식(`sp_snapshot_*`)은 [아래](#순위-테이블-배치-재계산--바꿔치기--100만-명)에 따로 정리했다.

## 측정 환경

같은 PC. 클라이언트는 Windows 11의 .NET 10, 서버는 WSL2 Ubuntu 26.04의 Redis 8.0.5와 MySQL 8.4.11. 둘 다 기본 설정이다(Redis는 AOF 꺼짐, MySQL은 `innodb_flush_log_at_trx_commit=1`, buffer pool 128MB). localhost 왕복이 약 0.2ms라 Redis 수치는 대부분 왕복 시간이다. 데이터는 점수 0~999,999 균등 난수(seed 42)이고, 각 조건은 한 번씩만 측정했다.

### 영속화 수준을 맞춘 쓰기 비교 — 10만 명, 점수 갱신, 2026-10-16

| 설정 | 순차 평균 ms | 동시 초당 처리 |
|---|---:|---:|
| Redis 기본 (AOF 꺼짐, RDB 스냅숏만) | 0.22 | 91,309 |
| Redis AOF `appendfsync everysec` | 0.23 | 70,927 |
| Redis AOF `appendfsync always` | **1.52** | 12,171 |
| MySQL `innodb_flush_log_at_trx_commit=1` (기본) | 2.92 | 4,067 |
| MySQL `innodb_flush_log_at_trx_commit=2` | 1.94 | 6,784 |

SP로 바꾸기 전(쿼리를 코드에 두던 때) 측정이다. 갱신 쿼리 자체는 같다. 원본: `results/20261016-01*.md`.

### 해석

1. **차이가 가장 큰 건 "내 순위"다.** Redis는 인원이 10배 늘어도 0.25ms 그대로다(O(log N)). MySQL `COUNT` 방식은 내 앞에 있는 사람 수만큼 인덱스를 읽는다. 그래서 상위 1%는 1ms 안팎이지만 하위 1%는 65ms다. 10만 명일 때 무작위 유저는 3.9ms였으니(2026-10-16) 인원에 비례한다. `EXPLAIN`으로 보면 `ix_score` 범위 스캔(커버링 인덱스)이고 rows가 대략 내 순위만큼 나온다.
   - 이유: Redis ZSET의 skiplist는 각 링크에 건너뛰는 원소 수(span)를 저장해서, 순위를 내려가면서 바로 더한다. InnoDB B+Tree는 노드에 하위 원소 수를 저장하지 않아서 순위를 알려면 세는 수밖에 없다.
2. **윈도 함수로 순위를 구하면 매번 전체 정렬이다.** 100만 명에서 1.2초가 걸린다. 요청마다 쓰면 안 되고, 정산 배치에서 한 번 계산해 테이블로 저장하는 용도다.
3. **상위 N명은 둘 다 빠르다.** MySQL도 `(score, user_id)` 인덱스를 역방향으로 100개만 읽으면 끝이라 인원과 무관하게 0.8ms 안쪽이다.
4. **쓰기 차이의 큰 부분은 영속화 보장 수준이다.** Redis 기본 설정은 매 쓰기를 디스크에 남기지 않는다. `appendfsync always`로 맞추면 Redis도 1.5ms로 느려진다. MySQL은 커밋마다 redo log를 fsync하는데, `flush_log_at_trx_commit=2`로 바꾸면 2.9ms → 1.9ms가 된다.
5. **동시 요청에서 MySQL 순위 조회는 무너진다.** 초당 258건, p99 315ms다. 순위 조회 한 번이 수십만 개 인덱스 항목을 읽어서 CPU와 buffer pool을 오래 잡기 때문이다.

## 깊은 페이지 조회 — 닉네임 포함 랭킹 목록, 100만 명, 2026-10-19

"랭킹 더 보기"로 offset 위치부터 10명을 **(user_id, 닉네임, 점수)** 로 보여 주는 비용이다. 닉네임은 일반적인 구조대로 별도 유저 테이블 `users(user_id PK, nickname)`에 있다.

| 방식 | 구현 |
|---|---|
| Redis | `ZREVRANGE` + 닉네임 해시 `HMGET` (2회 왕복) |
| MySQL 단순 JOIN | `sp_ranking_get_page_named`: `ranking JOIN users … ORDER BY score DESC, user_id DESC LIMIT 10 OFFSET n` — 가장 흔하게 짜는 쿼리 |
| MySQL 지연 조인 | `sp_ranking_get_page_named_deferred`: 안쪽에서 `ranking` 인덱스만으로 10명을 고르고, 그 10명만 `users`와 JOIN |
| MySQL 순위 테이블 | `sp_snapshot_get_page_named`: `ranking_snapshot`에서 `rnk BETWEEN n+1 AND n+10` + `users` JOIN |

원본: `results/20261019-0042-users1000000-deep-page.md`. 네 방식의 결과는 offset 8곳 모두 일치했다.

| offset (순위) | Redis | MySQL 단순 JOIN | MySQL 지연 조인 | MySQL 순위 테이블 |
|---:|---:|---:|---:|---:|
| 500 | 0.54ms | 1.1ms | 0.77ms | 0.72ms |
| 5,000 | 0.50ms | 5.0ms | 1.2ms | 0.72ms |
| 10,000 | 0.51ms | 9.3ms | 1.7ms | 0.78ms |
| 50,000 | 0.49ms | 43.8ms | 5.6ms | 0.72ms |
| 100,000 | 0.52ms | 89.9ms | 10.7ms | 0.78ms |
| 300,000 | 0.54ms | 275ms | 31.5ms | 0.75ms |
| 500,000 | 0.49ms | 464ms | 50.1ms | 0.73ms |
| 900,000 | 0.50ms | **823ms** | 91.5ms | 0.74ms |

### 실행 계획 (offset 900,000)

| 쿼리 | 테이블 | type | key | rows | Extra |
|---|---|---|---|---:|---|
| 단순 JOIN | ranking | index | ix_score | 900,010 | Backward index scan; Using index |
| | users | eq_ref | PRIMARY | 1 (**행마다**) | |
| 지연 조인 (안쪽) | ranking | index | ix_score | 900,010 | Backward index scan; Using index |
| 지연 조인 (바깥) | users | eq_ref | PRIMARY | 1 (**10명만**) | |
| 순위 테이블 | ranking_snapshot | range | ix_rnk | 10 | Using index condition |
| | users | eq_ref | PRIMARY | 1 | |

### 해석

1. **가장 흔하게 짜는 단순 JOIN이 제일 느리다.** 실행 계획은 인덱스를 잘 타지만, MySQL은 `LIMIT … OFFSET`을 JOIN이 끝난 결과에 적용한다. 그래서 버릴 90만 행도 하나하나 `users`를 PK로 찾아 JOIN한 뒤에 버린다. 90만 번의 PK 조회가 붙어서 offset 90만에서 823ms다.
2. **지연 조인은 JOIN 비용을 10건으로 줄인다.** 안쪽 쿼리가 커버링 인덱스만 읽어 10명을 고르고, 그 10명만 `users`와 JOIN한다. 같은 offset에서 단순 JOIN보다 9배 빠르다(92ms). 그래도 offset만큼 인덱스를 읽고 버리는 비용(O(offset))은 남는다.
3. **순위 테이블은 offset과 무관하다.** `rnk` 범위로 그 위치를 바로 찾아서 어느 offset이든 0.7ms다. Redis(0.5ms, 닉네임까지 2회 왕복)와 비슷하다.
4. **다음 페이지만 필요하면 키셋 페이지네이션도 있다.** 직전 페이지 마지막 행의 (score, user_id)를 받아 `WHERE score < @s OR (score = @s AND user_id < @u) ORDER BY score DESC, user_id DESC LIMIT 10`으로 읽는다. "다음 페이지"는 offset과 무관해지지만 "N번째 페이지로 바로 이동"은 안 된다. 키셋 방식은 측정하지 않았다.

## 순위 테이블 배치 재계산 + 바꿔치기 — 100만 명

MySQL만으로 랭킹을 할 때 흔한 방식이다. 점수는 원본 `ranking`에 쌓고, 주기적으로 순위를 계산해 순위 테이블에 넣는다. 게임은 순위 테이블만 조회한다.

- 순위 테이블: `ranking_snapshot(user_id PK, score, rnk UNIQUE)`
- 재계산 (`sp_snapshot_rebuild_swap`):
  1. `CREATE TABLE ranking_snapshot_new LIKE ranking_snapshot`
  2. `INSERT … SELECT user_id, score, ROW_NUMBER() OVER (ORDER BY score DESC, user_id DESC) FROM ranking`
  3. `ANALYZE TABLE`
  4. `RENAME TABLE ranking_snapshot TO …_old, ranking_snapshot_new TO ranking_snapshot` (여러 테이블 RENAME은 한 문장이라 원자적이다)
- 조회: 내 순위는 PK(`sp_snapshot_get_rank`), 상위 N명·깊은 페이지는 `rnk BETWEEN` 범위(`sp_snapshot_get_range`), 주변은 자기 JOIN(`sp_snapshot_get_around`)

원본: `results/20261019-0041-users1000000-snapshot.md`. Redis와 결과 비교(순위 200건, 상위 100명, 주변 20건, 깊은 페이지) 불일치 0건.

### 조회 속도 — 순차 200회 평균 ms / 32개 동시 초당 처리

| 연산 | Redis | MySQL 실시간 COUNT | MySQL 순위 테이블 |
|---|---:|---:|---:|
| 내 순위 (무작위 유저) | 0.24 | 33.6 | 0.71 |
| 내 순위 (하위 1%) | 0.26 | 63.5 | 0.72 |
| 상위 100명 | 0.35 | 0.75 | 0.82 |
| 내 주변 ±5명 | 0.54 | 38.8 | 1.19 |
| 깊은 페이지 (90만 등부터 10명) | 0.26 | 97.6 | 0.72 |
| 내 순위 동시 초당 처리 | 45,743 | **229** | 11,714 |

### 재계산 방식별 비교 — 재계산 중 순위 조회 8개 작업이 계속 돈다

| 방식 | 재계산 (부하 없음 / 있음) | 조회 실패 (못 찾음) | 조회 최대 지연 |
|---|---:|---:|---:|
| 새 테이블 + RENAME 바꿔치기 (`sp_snapshot_rebuild_swap`) | 4.7s / 11.4s | 0 | 72ms |
| TRUNCATE 후 다시 채우기 (`sp_snapshot_rebuild_truncate`) | 4.9s / 10.2s | **83,254건 / 92,533건 (90%)** | 73ms |
| 한 트랜잭션에서 DELETE 후 다시 채우기 (`sp_snapshot_rebuild_delete`) | 12.6s / 30.6s | 0 | 21ms |
| 바꿔치기 + 순위 테이블을 읽은 트랜잭션이 RENAME을 2초 막음 | — | 0 | **2,094ms** |

### 재계산 중 원본 점수 갱신 — 갱신 8개 작업이 계속 돈다 (바꿔치기 방식)

| 재계산 세션 격리 수준 | 재계산 중 갱신 수 | 오류 | p99 | 최대 지연 |
|---|---:|---:|---:|---:|
| REPEATABLE READ (MySQL 기본) | 953 | **데드락 3건** | 606ms | **5,132ms** |
| READ COMMITTED | 8,557 | 0 | 30ms | 70ms |

### 해석

1. **효과는 "순위를 미리 계산"에서 나온다.** 내 순위가 34~64ms에서 0.7ms로, 동시 처리는 초당 229건에서 11,714건으로 늘었다. 깊은 페이지도 `OFFSET` 대신 `rnk` 범위라 순위와 무관하다. Redis와는 3~4배 차이(왕복과 SQL 처리 오버헤드)라 실시간성만 포기하면 충분히 쓸 만하다. 대가는 **재계산 주기만큼 순위가 늦다**는 것이다.
2. **바꿔치기는 속도가 아니라 "조회 안전성" 때문이다.** TRUNCATE 후 채우면 채우는 동안 순위 테이블이 비어서, 그 사이 조회의 90%가 "랭킹에 없음"이었다. 바꿔치기는 조회가 항상 이전 아니면 새 테이블을 봐서 실패가 0건이다.
3. **MySQL(InnoDB)은 한 트랜잭션 DELETE + INSERT도 조회 실패가 없다.** MVCC라 커밋 전까지 조회는 이전 행을 읽는다. 대신 행마다 undo를 남겨서 2.5배 느리고(12.6s), 그동안 undo 로그가 커진다. MSSQL 기본 설정(READ COMMITTED, 스냅숏 격리 꺼짐)에서는 이 방식이면 조회가 커밋까지 잠금에 막힌다. MSSQL에서 리네임 방식을 쓰는 이유가 이쪽일 가능성이 크다(MSSQL은 측정하지 않았다).
4. **RENAME은 메타데이터 잠금(MDL)이 필요하다.** 순위 테이블을 읽은 트랜잭션이 열려 있으면 RENAME이 기다리고, 그 뒤에 온 조회도 전부 RENAME 뒤에 줄을 선다. 2초 막히면 조회도 2초 멈췄다. 순위 테이블을 오래 읽는 정산·통계 쿼리를 같은 시각에 돌리지 않고, `lock_wait_timeout`을 짧게 걸어 실패하면 재시도한다(기본값 1년).
5. **재계산 세션은 READ COMMITTED로 돌린다.** 기본(REPEATABLE READ + binlog)에서는 `INSERT … SELECT`가 원본 행마다 공유 잠금을 건다. 그래서 재계산 내내 점수 갱신이 막히고(최대 5.1초) 데드락도 났다. READ COMMITTED면 원본을 잠금 없이 읽는다.
6. **바꿔치기 전에 `ANALYZE TABLE`을 한다.** 새로 채운 테이블은 통계가 "빈 테이블"(rows=20)이다. 그래서 옵티마이저가 `rnk` 인덱스를 두고 전체 스캔 + filesort를 골랐고, 상위 100명 첫 조회가 106ms(정상 0.8ms)였다. InnoDB가 백그라운드에서 통계를 다시 계산하기 전까지 느리다.

## 설계로 옮기면

- **실시간 순위**(내 순위, 주변 순위를 자주 묻는 랭킹)는 Redis ZSET이 맞다. MySQL로 같은 일을 하면 인원에 비례해 느려진다.
- **원본과 정산은 MySQL**에 둔다. Redis는 AOF를 켜도 마지막 1초를 잃을 수 있고(everysec), 보상 지급 근거는 트랜잭션이 되는 DB에 있어야 한다.
  - 점수 변경 → DB 저장 → Redis `ZADD` 순서로 반영한다. Redis가 날아가면 DB에서 다시 채운다. 100만 명 적재는 Redis 5.8초였다.
  - 시즌 종료 정산은 DB에서 윈도 함수로 한 번 계산해 결과 테이블에 저장하고, 보상은 그 테이블 기준으로 지급한다.
- **MySQL만 써야 한다면** 순위를 실시간으로 계산하지 않는다.
  - 주기적으로(예: 5분, 일 단위) 순위 테이블을 배치로 만들고 조회는 그 테이블에서 읽는다. 상위 N명은 인덱스만으로 실시간 조회해도 된다.
  - 재계산은 새 테이블 + `ANALYZE` + `RENAME` 바꿔치기로 하고, 세션은 READ COMMITTED로 둔다.
  - 목록에 닉네임처럼 다른 테이블의 열이 필요하면 단순 JOIN 대신 지연 조인이나 순위 테이블을 쓴다.
- **동점 처리**는 정책이 먼저다. 여기서는 user_id로 정했지만 보통은 "먼저 달성한 사람 우선"이다. Redis는 점수 하나에 정렬 기준이 하나라서 `점수 × 2^k + (기준 시각 − 달성 시각)`처럼 합성 점수로 넣는다. double이라 정수로 정확한 범위는 2^53까지다.
- **더 커지면**(수천만 명, 키 하나가 수 GB) 점수 구간이나 서버별로 키를 나누고, 하위 구간은 "상위 x%" 같은 근사 순위로 보여 준다. 10만 명 ZSET이 약 11MB(`MEMORY USAGE`)였으니 100만 명은 100MB 남짓이다.
- **SP로 둘지 코드에 둘지는 팀 문화다.** MSSQL 쪽은 SP 중심이 일반적이다(DBA 검토, 실행 권한만 부여, 서버 재배포 없이 쿼리 수정). MySQL은 코드의 파라미터 쿼리가 더 흔하다. MySQL SP는 실행 계획 캐시가 연결마다 따로라 성능 이점이 작다. 이 프로젝트는 쿼리와 인덱스를 한눈에 보려고 SP로 정리했다. 쿼리 자체는 같아서 측정값은 SP 전환 전과 비슷했다.

## Kafka → Redis 랭킹 반영 (`src/Ranking.Kafka`)

게임 서버가 "점수 획득" 이벤트를 Kafka에 발행하고, 랭킹 갱신기(컨슈머 그룹)가 받아서 Redis ZSET에 더하는 구조다. Kafka 4.3.1(KRaft 단일 노드, ZooKeeper 없음)을 WSL에 서비스로 설치했다.

```bash
dotnet run -c Release --project src/Ranking.Kafka -- --users 10000 --events 200000
```

| 항목 | 구현 |
|---|---|
| 토픽 | `score-events`, 파티션 4개 |
| 키 | user_id → 같은 유저는 항상 같은 파티션 → **유저별 순서 보장** (파티션 = 레인 고정과 같은 개념) |
| 프로듀서 | `acks=all`, `enable.idempotence=true` (재전송으로 브로커에 중복이 쌓이는 것을 막음). 로컬 큐가 차면 `Poll` 후 재시도 |
| 컨슈머 | 자동 커밋 끔. 500건 배치로 받아 Redis에 파이프라인으로 반영 → **반영이 끝난 뒤 커밋** (at-least-once) |
| 멱등 반영 | 이벤트에 유저별 seq를 붙이고, Lua 스크립트로 "마지막 seq보다 클 때만 ZINCRBY + seq 기록"을 원자적으로 실행 |

### 결과 (2026-10-16, 이벤트 20만 건, 유저 1만 명)

1. 발행: 초당 약 14만~23만 건(실행마다 차이), 전송 실패 0건. 파티션별 약 5만 건씩 고르게 나뉨
2. 컨슈머 A가 3만 건을 Redis에 반영하고 2만 건까지만 커밋한 뒤 종료 (장애 재현)
3. 같은 그룹으로 B1·B2를 시작 → 커밋 위치부터 다시 받아 **1만 건을 다시 받음**. 멱등 반영이 1만 건을 전부 걸러냄. 한 컨슈머 안에서 유저별 순서 위반 0건. Redis 반영과 커밋을 포함해 초당 약 1만 6천 건
   - 이번 실행에서는 B2가 먼저 합류해 파티션 4개를 다 처리했고 B1은 받은 게 없었다. 파티션이 둘로 나뉘는 모습은 이번 실행에서 확인하지 못했다
4. 최종 점수 검증:

| 반영 방식 | 점수가 틀린 유저 | 초과 지급된 점수 합 |
|---|---:|---:|
| seq 확인 후 반영 (Lua, 멱등) | 0 | 0 |
| 받은 대로 ZINCRBY | 2,446 | 505,629 |

### 면접에서 말할 포인트

- Kafka는 기본이 **at-least-once**다. "반영 → 커밋" 사이에 죽으면 다시 받는다. 순서를 "커밋 → 반영"으로 바꾸면 at-most-once라 유실된다. 그래서 반영 쪽을 멱등으로 만든다.
- 프로듀서 멱등성(`enable.idempotence`)은 **브로커에 같은 메시지가 두 번 쌓이는 것**만 막는다. 컨슈머가 다시 받는 중복은 애플리케이션이 막아야 한다.
- 멱등 키는 유저별 seq로 했다. 유저를 소유한 서버 하나가 seq를 매기고, 같은 유저는 같은 파티션이라 순서대로 오기 때문에 "마지막 seq보다 작거나 같으면 버림"만으로 충분하다. 이벤트 ID를 따로 저장하는 방식보다 저장 공간이 유저 수만큼만 든다.
- 확인과 반영은 Lua 스크립트 하나로 원자적으로 했다. 둘을 따로 보내면 그 사이에 다른 컨슈머가 끼어들 수 있다(리밸런스 직후).
- 보상 지급처럼 돈이 걸린 처리는 같은 원리를 DB에 적용한다: 유니크 키(이벤트 ID) + 같은 트랜잭션에서 반영과 처리 기록.

## 측정의 한계

- 클라이언트와 서버가 같은 PC라 네트워크 지연이 실제보다 작고, CPU를 서로 나눠 쓴다.
- 두 서버 모두 기본 설정이다. MySQL buffer pool(128MB)은 100만 명 테이블이 다 들어가는 크기라 디스크 읽기는 거의 없었을 것이다(확인은 안 했다).
- 각 조건을 한 번씩만 측정했다. 수치는 차이의 크기(몇 배인지)를 보는 용도로만 쓴다.
- `results/`에는 이전 측정도 남아 있다: SP 전환 전 결과(2026-10-16~18), 외부 자료 스키마(`KEY(score)`만 있는 단일 테이블)를 재현한 깊은 페이지 결과(`20261017-0034-…`).
