# Kafka → Redis 랭킹 반영 데모

- 일시: 2026-10-16 02:51
- 토픽 `score-events` 파티션 4개, 컨슈머 그룹 `ranking-updater`
- 이벤트 200,000건 (유저 10,000명, 점수 획득량 1~100), 키 = user_id
- 서버: WSL2 Ubuntu의 Kafka 4.3.1 (KRaft 단일 노드), Redis 8.0.5. 클라이언트: Windows .NET 10.0.12, Confluent.Kafka

## 1. 발행 (acks=all, 프로듀서 멱등성 켬)

- 200,000건 / 0.87s = **초당 230,865건**, 전송 실패 0건
- 파티션별 건수: P0=50,202, P1=49,893, P2=50,130, P3=49,775 (키 해시로 고르게 나뉜다)

## 2. 컨슈머 A — 30,000건 반영, 20,000건까지만 커밋하고 종료 (장애 재현)

- A: 받은 이벤트 30,000, 반영 30,000, 커밋 20,000, 받은 파티션 P3
- 커밋 안 된 10,000건은 **이미 Redis에 반영됐지만** 브로커는 처리 안 된 것으로 안다

## 3. 컨슈머 B1·B2 — 같은 그룹으로 동시에 시작해 남은 이벤트 처리

- B1: 받은 이벤트 0, 반영 0, 중복이라 건너뜀 0, 받은 파티션 -, 순서 위반 0
- B2: 받은 이벤트 180,000, 반영 170,000, 중복이라 건너뜀 10,000, 받은 파티션 P0,P1,P2,P3, 순서 위반 0
- 합계 180,000건 / 11.13s (대기 시간 제외) ≈ 초당 16,174건 (Redis 반영·커밋 포함)
- 다시 받은 이벤트 = B가 받은 180,000 − A가 아직 안 받은 170,000 = **10,000건** (A가 반영만 하고 커밋 못 한 만큼)

## 4. 최종 점수 검증 (기대값 = 유저별 점수 획득량 합)

| 반영 방식 | 점수가 틀린 유저 | 초과 지급된 점수 합 |
|---|---:|---:|
| seq 확인 후 반영 (Lua, 멱등) | 0 | 0 |
| 받은 대로 ZINCRBY | 2,446 | 505,629 |

> 다시 받은 이벤트는 멱등 처리 덕분에 seq 확인에서 걸러지고, 멱등 처리가 없으면 그만큼 점수가 두 번 더해진다.
